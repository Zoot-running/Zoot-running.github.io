# 1. 解决方向
Agent的三个核心问题都指向了任务过大、过于复杂导致Agent无法承接任务。联系现实，当一个人解决不了问题的时候，就要考虑加人，同时，这个过程会引入管理成本，但是任务是能够被完成的。从软件工程的角度看，是将任务模块化，然后解耦模块，之后就能够独立的处理模块，如此递归下去，总会出现能够很容易解决，或者说能够由单个Agent解决的子任务。

因此，总体的解决方向就是使用Agent集群（Agent cluster）来执行复杂任务。Agent集群是能够同时解决3个核心任务中的两个的，另外一个也有希望改善：
1) 上下文窗口：多个Agent起了多个会话，不同会话使用不同上下文窗口，每个Agent只关注自己的子任务，子任务又相互正交、解耦，所以相当于一个任务由N个上下文窗口执行，突破上下文窗口限制；
2) 性能效率：多个Agent可以并行执行，解决效率问题；
3) 成本控制：多Agent必然会引入管理成本，但是同时不同Agent能够使用不同模型，存在降本的可能。

使用Agent集群来处理复杂任务，会有2个关键问题：
1) 如何划分任务？从软件工程的经验来看模块一个功能正交，任务的执行路径也应该正交；
2) 如何规划执行？毕竟子Agent的执行都在同一个环境中，执行的作用都在一个环境，难免相互影响，如何发现和消除这些影响？

显然，这两个问题已经上升到系统思维和项目管理层面了，无法通过一些静态的约束实现。这里不得不吐槽一句，openai新搞的Harness Engineering只能是临时性的解决方案，因为它只是给了一些相对静态的逻辑和约束，没有意识到根本的问题在于当前的Agent缺乏系统性思维。不把系统性思维在架构层面灌给AI，是无法解决根本问题的。
# 2. Agent cluster Architecture
Agent cluster从架构上大致可以分为三层：
<div style="text-align: center;"> <img src="../../resource/02-AI学习与实践/01-架构/智能架构-Agent Cluster.drawio.svg"> </div>
- 交互层，负责和用户交互，不断学习用户习惯/意图，美化最终输出的结果，这一层只有一个Agent，专门负责交互；
- 规划调度层，负责对任务进行合理的分解、规划、动态调度、重规划，并且保证用户意图不会出现漂移；
- 任务执行层，接受规划调度层下发的子任务，仅了解子任务的上下文，通过直接规划执行步骤或进一步分解子任务来完成任务。
这一套架构执行一个动态的任务分解-步骤规划-执行反馈-重规划的步骤，保证任务能够完成，同时用户意图没有漂移。
总体来讲，任务的执行分成2个阶段：
<1> 规划阶段，给出实现任务的详细方案
1) 用户意图识别，这个阶段由模型结合用户过往习惯或其他上下文信息，识别用户需要执行的任务；
2) 任务规划，获取需要执行的任务，收集系统相关信息，由任务规划Agent根据任务规划执行任务的步骤；
3) 任务总体规划意图保持，将规划的步骤发送给意图保持Agent，判断步骤执行后是否能够实现用户的意图，如不能，则打回重新规划；
4) Agent规划，如果意图保持Agent认为没有问题，则对每个步骤进行识别，是否需要子Agent承接相关步骤，还是由Agent调用工具直接执行；
5) 计划汇报，如果本Agent的所有步骤都没有使用子Agent的话，就把任务规划上报给布置任务的Agent；
6) 任务规划汇总，Agent收到所有执行单步骤的Agent的具体执行步骤以后，汇总为本Agent的总体执行步骤，汇总不是简单的步骤连接，需要综合考虑不同Agent对相同资源的使用、步骤间依赖关系，任务规划汇总可能会取消掉部分Agent的部分步骤，来达到全局的任务详细步骤最优。同时，步骤之间的依赖也会传递给子Agent，让子Agent之间建立联系，方便遵从依赖；
7) 任务详细规划意图保持：意图保持Agent对详细规划做出裁判，判断步骤执行后是否能够实现用户的意图，如不能，返回任务规划步骤，重新规划；
8) 所有任务执行步骤确定，开始执行阶段
<2>执行阶段，处置执行时出现的状况
9) 如果执行中出现了意外，则本Agent尝试解决，如果不能则上升到父Agent，由任务调度Agent综合考虑；
10) 关键步骤汇报，对于存在依赖的步骤，执行后汇报给父任务调度Agent，便于父任务调度Agent理解当前任务执行进度；
11) 任务执行结束，获取结果，做输出美化，返回给用户。
# 3. 仍然存在的问题
架构看起来很美，但是在实现之前就能够观察到几个问题：
1) Agent如何划分？当前的Agent是一个专家系统，用于执行一类型的任务，它的权限往往是全域的，但是在Agent Cluster架构中这显然是个问题，不同的子任务分配给不同的Agent，规划相同的步骤，会被重复执行；规划冲突的步骤，导致最后的任务执行失败。最好的方案是Agent按域划分，但是这和Agent的设计理念又冲突了。未来需要一种方案，对Agent做访问控制，在它执行某个任务的时候，只能访问一定的区域；
2) 任务如何保证执行任务的正交？当前架构是依赖不断的进行规划迭代，但是这非常消耗Token。
这些问题仍然需要在实践中探索，似乎Agent Cluster的架构，与现代企业的管理已经具备了一定的相似性，如何建立通用的、有效的架构，仍旧需要深入的分析。
